# Upgrading to 0.88

How to move a deployment and the code built on the `systemprompt` crates from 0.87 to 0.88. This release turns the platform into a kernel and a set of capabilities composed at build time: an extension is `metadata()` plus one `contribute(&mut Contributions)`, a binary is a `Composition`, every host value is a typed kernel seed, and the facade's `full` feature is replaced by `reference`. It also adds per-node connection budgets, role-scoped schema installation, load shedding on by default, a longer stream drain and an exactly-once scheduler claim.

## Operator actions

| Area | Action | Required |
|---|---|---|
| Database | Run the release's forward-only migrations (`infra db migrate`, or `infra services serve` with `migrate_on_boot`) before serving | Yes |
| `infra db migrate` exit status | The command exits non-zero when it holds a member back because the database records migrations the binary does not know, and names each such member. Run the release that wrote them, or add a tombstone for a migration no release ships | Review, in deploy scripts |
| Facade feature | Replace `features = ["full"]` with `features = ["reference"]` in every crate that depends on `systemprompt` | Yes, if `full` is named |
| Supported compositions | Build one of the compositions listed in [feature flags](../reference/feature-flags.md#supported-compositions); other feature sets are unsupported | Review |
| `server.max_in_flight` | Load shedding is on by default at 4096 concurrent requests per replica; an open response stream counts until it closes. Set a value sized for the node, or `null` for no ceiling | Review |
| `server.shutdown.longest_stream_secs` | The drain now waits up to 600 s while a response stream is open, so the default shutdown budget is 612 s. Raise the orchestrator's termination grace (`terminationGracePeriodSeconds`, 30 s by default on Kubernetes) above the total the server logs at boot, or lower this value | Yes, on Kubernetes |
| `observability.otlp` | A build without the `otel` feature refuses to boot when the profile sets this block, instead of dropping every span. Build with the facade's `otel` feature (in `full`), or remove the block | Yes, on reduced compositions |
| `database.connection_budget` | New, optional: the most Postgres connections one node holds, children included. Boot is refused when the pinned pool sizes exceed it | No |
| `database.schema_install_roles` | New, optional: the roles that install the schema at boot; every other role verifies it | No |
| `rate_limits.memory_capacity` | New, optional: callers tracked per node in per-replica windows (default 262144) | No |
| Scheduler config | Boot is refused when `scheduler.jobs` or `scheduler.bootstrap_jobs` names a job no admitted member contributes: `otlp_export`, removed in this release, or a job of a member the profile disables. `admin config validate` lists each such name as not contributed. Remove the entry | Yes, if such a job is named |
| Scheduler | A `cluster` job runs exactly once per instant across replicas and a `node` job once per instant per replica while the database is reachable; under an outage a tick is skipped. Jobs that relied on a second run in a short window run once | Review |
| `server.instance_id` on a local profile | A local profile that sets none and has no platform hostname resolves `local-<profile name>-<machine fingerprint>` (a hash of the OS machine id, else the host name) instead of a random id per process: the server, its services and a CLI on the same machine share it, so the CLI sees the services the running server started, and another machine never resolves it. `infra services cleanup` reaps service rows only when no live server holds the instance claim; otherwise it leaves them and says so. Markers named `instance-<32 hex>` that earlier releases left under `<storage root>/.systemprompt/instances/` are no longer pruned; they affect only the boot-time shared-storage diagnostic, which may warn that a local root looks shared. Delete them to silence it | Review, on local profiles |
| Rate limits | Identity-keyed windows are shared across replicas when the users member provides them (the reference composition does); address-keyed throttles are per replica, so the effective limit across N replicas is N times the published rate | Review |
| Extensions and installs | Port each member to `contribute` and each binary to `Composition`; see [authoring extensions](authoring-extensions.md) and the entries below | Yes, for custom members |

## Every breaking change

Each entry below is one breaking change of this release, with its migration where code must change. They are grouped by area; the same text, per crate, is under `### Breaking` in `CHANGELOG.md` and each crate's changelog. This list has 198 entries.

## API

- `discovery_router` and `probes_router` return `Result<Router, LoaderError>`, and an extension router whose declared policy admits no caller, whose context contradicts its policy, or whose body limit exceeds the 2 MiB server default fails boot with `MountError`. Migrate by propagating the error and lowering the declared limit.
- the API reads the session store (users), behavioural scorer (analytics), content catalog (content), IP-ban store (users) and MCP registry (mcp) from the extension state. `SessionMiddleware::new` returns `Result<_, LoaderError>` and boot refuses without a session store or an IP-ban store. Extension routers are no longer handed `Option<Arc<AiService>>` or `Arc<ArtifactIngest>` as axum extensions; `/health/detail` reports enabled extensions' readiness checks under `checks.extensions`. `IngestionService::new` takes the frontmatter processors. Migrate by reading `Arc<AiService>` and `Arc<ArtifactIngest>` from the resolved state of the route set.
- `repository::session_usage` and the `From<UserError> for ApiHttpError` conversion are removed and the API no longer depends on `systemprompt-users`; the session usage counters are the `DynSessionUsageCounters` the `users` member provides.
- Every served and reserved `/api/v1` path is spelled once in `ApiPaths`; `systemprompt_documents::http::surface::ISSUES_PATH` and the unused `SystempromptClient::verify_token` are removed.

## Agent config writes

- An agent create or update is validated from an exclusively created, unpredictably named staged file before it is renamed over the live file, so a refused change never shows on disk. The check closure takes `&StagedAgentFile` and validates through `ConfigLoader::with_staged`; a staged file that cannot be removed after a refusal is `ConfigWriteError::RejectedStagedNotRemoved`, carrying both causes.

## Agent routes

- The webhook broadcasts, the agent SSE streams and the well-known agent cards move from `systemprompt-api` to the `agent-http` member (`systemprompt-agent-entry`), mounted through the new `systemprompt_extension::router::AgentSurface` builder with each route's policy, context and role group unchanged. With `agent-http` disabled they answer 404. `systemprompt_api::routes::webhook`, `systemprompt_api::routes::stream::stream_router` and `systemprompt_api::routes::wellknown::agent_cards` are removed; build the routers with `systemprompt_agent_entry::http::{webhook, stream, agent_cards}`.

## Agent runs

- The `/api/v1/agent-runs` routes are declared by the `agent_runs_api` member in the new `systemprompt-agent-runs-entry` crate, with the user gate, user context, the `agent_runs` rate limit on the tasks budget and the `Agent` route group, so the `all`, `api` and `worker` roles serve them. `systemprompt-api` and `systemprompt-cli` no longer have an `agent-runs` feature or depend on the agent-runs crates. A profile that disables `agent_runs_api` mounts no agent-runs route (404); one that disables `agent_runs` while `agent_runs_api` stays enabled is refused at boot. `admin agents run` reads its agent-run launcher from the host's resolved state; without one the agent processes every task itself. Migrate by enabling the facade's `agent-runs` feature in place of `systemprompt-api/agent-runs` / `systemprompt-cli/agent-runs`.

## Agents

- The agent capability's conversation routes and commands are contributed by the `agent-http` composition member (`systemprompt-agent-entry`). `/api/v1/core/contexts`, `/api/v1/core/tasks`, `/api/v1/core/artifacts` and `GET /api/v1/agents/registry` keep their paths, policies, request contexts, rate limits, body limits and role group; a profile that disables `agent-http` mounts none of them (404), and one that disables `agent` while `agent-http` stays enabled is refused at boot. `admin agents`, `core contexts` and `core artifacts` are member groups under their reserved paths with the `services-tree`/`caller-session` (agents), `caller-session`/`session-context` (contexts) and `caller-session` (artifacts) grants. `admin agents delete` no longer stops a process: it refuses a running agent and names `infra services stop agent <name>`, and `--force` is removed. `admin agents status` reads the service table without building an orchestrator. `admin agents message` and `admin agents task` present the caller's session only to the profile's own API URL; `--url` is removed from both. `admin agents tools` is removed. The spawned agent process runs as `admin agent-host run --agent-name <n> --port <p>` (kernel child host); `admin agents run` is removed. An agent spawned by an earlier release is still recognised by its pid and spawn marker at shutdown and reconcile.

## Analytics

- The analytics member provides `Arc<AnalyticsRepositories>` and `Arc<AnalyticsService>`, and the analytics stream is handed its broadcaster by the composition as the subscribe-only `AnalyticsSubscription`: a route set at the engagement base cannot resolve it, and a missing handle refuses boot. The request-analytics middleware skips the part of the record whose provider is absent. `AnalyticsRepositories::new(db, sessions, event_log)` and `SessionSignalsRepository::new(db, owner, events)` no longer take the content catalog; `get_total_content_pages`, `collect_analysis_input` and `SessionBehaviourScorer::score` take it per call. Migrate by passing the `DynContentCatalogStats` the content member provides.

## Build

- `systemprompt-content` and `systemprompt-files` no longer depend on `systemprompt-cloud` (they read the storage constants from `systemprompt_manifest::paths::constants::storage`), and `systemprompt-cloud-entry` no longer depends on `systemprompt-gateway`: `GATEWAY_POLICIES_PLANE` moves to `systemprompt_models::ai`. Migrate by importing the constant from there.

## CLI

- `args::Commands::Build` and `Commands::serves_api` are removed and `args::Cli::command()` no longer contains registered groups; `admin::setup::{docker_compose, postgres_access, ddl}` move to `shared::{docker_compose, postgres_access, ddl}`, `admin::setup::catalog` and `admin::config::services_io::write_gateway` to `systemprompt_cloud::provider_catalog`, `admin::config::config_section::{read_yaml_file, write_yaml_file}` to `systemprompt_config::yaml_document`, `admin::session::types::ProfileInfo` to `shared::profile` and `plugins::mcp::types::McpToolEntry` to `commands::shared::mcp_tools`. Migrate by building the command tree with `args::command(&registry)` over the admitted command registry and importing from the new paths.
- A command group or leaf runs as `run(&dyn CommandHost) -> CommandOutput` and the CLI renders the output once; groups are contributed with `Contributions::command` (`CommandDecl`) and request kernel grants with `requesting`. `CommandError` is no longer a tuple struct (`CommandError::new`, `with_output`, `output`) and `CommandOutput` gains `with_note`, `notes` and `rendered`. On a bare `--database-url` run a member command runs only when it declares `DbUrlRouting::Direct` (over every linked member, none disabled) and is otherwise refused with `ProfileRequired`; a cloud profile reaching its database through `external_db_access` is admitted against that profile, so a disabled member's command is refused with `CommandDisabled` and `infra db migrate` installs no disabled member's schema; `infra jobs list`/`show` need a profile; `infra db migrate*`, `migrations` and `doctor` run over the admitted composition, and on a bare `--database-url` run install every linked member's schema. `--json` is removed from the four `infra db` migration subcommands (use the global `--json`). `plugins validate` and `plugins capabilities templates|tools` are removed; `plugins list|show|config|capabilities` report the admitted members, and `plugins seams` lists the admitted composition member by member (`--seam` is `--member`). Migrate a command group to `CommandHost`/`CommandOutput` and pass `--json` before the subcommand.
- A member command reaches kernel-held material only through a grant listed on its reserved CLI path. `CommandHost::profile` is served to a member command only under `boot-profile` (the `cloud` path); every other member command is refused it. Two grants are added: `services-tree` (`core marketplace`, `core plugins`, `core skills`) serves the active services root with the published API URL and site GitHub link through `CommandHost::services_tree`, without a database; `caller-session` (`plugins mcp`) serves the CLI caller's own session token through `CommandHost::caller_session`. `local-export` also serves the profile's exports directory through `CommandHost::export_dir`. An install command holds no grant.
- `plugins mcp` is contributed by the `mcp-http` composition member (`systemprompt-mcp-entry`) with the `caller-session` grant; a profile that disables `mcp-http` refuses the group at dispatch. The commands read the `mcp` member's read-only `McpServiceObserver` and registry and can no longer start, stop or signal a server: `tools`, `call` and `validate` reach only servers the service table records as running (start one with `infra services start`; `admin mcp` remains the control surface). `tools` and `call` present the caller's own session token over an anonymous request context, and `tools` resolves the session only when a queried server requires OAuth. `list` and `status` find build binaries under the profile's build directory instead of a project root discovered from the working directory. `tools --schema` on non-JSON output returns the schema view in place of the table, and a failing `call` or `validate` returns its card with the error, rendered once.
- `core marketplace`, `core plugins` and `core skills` are contributed by the `marketplace-http` composition member (`systemprompt-marketplace-entry`, feature `cli`) under the `services-tree` grant; a profile that disables `marketplace-http` refuses the three groups at dispatch. `core plugins` and `core marketplace explain` read the loaded services configuration instead of reloading it from the profile and need no database. `core skills` boots the application context (it is a full, remote-eligible command) and reads managed skills through the organization skill resolver the `managed_resources` member provides; with no reachable database it lists disk skills only. A failing `core plugins validate` returns its report with the error, rendered once.
- `admin keys issue-plugin-token` is contributed by the `identity-http` member under its `admin keys` group and mints through the conferred plugin-token minter. With `--email` omitted, the token is minted for the caller's CLI session user instead of the cloud-credentials email.

## Child supervision

- A supervised agent or MCP child is signalled only when its environment carries the service marker and the boot nonce of the process that spawned it, recorded with its pid in the `services` row (database migration 017 adds `services.spawn_nonce`); ownership is checked again immediately before a forced kill, so a pid that changed owner during the grace period is reported `NotOurs` and never killed. A row recorded by an earlier release (a pid and no nonce) matches only a process carrying the service marker and no nonce, until the child is next restarted. Every agent and MCP stop waits `server.shutdown.child_grace_secs` instead of a fixed five seconds. `admin agents delete` treats an agent as running only while its recorded pid proves to be that agent's child. Migrate by passing a `ChildClaim` to `subprocess::owns`/`stop_owned` and recording `Spawner::nonce()` with every pid.

## Cloud

- a `cloud doctor` check contributed by a member receives secret presence and read-only, purpose-typed probes (`DoctorProbes`) in place of a handle map holding the tenant database pool. The probes read through a session with `default_transaction_read_only` on. Core and install members' checks run against the same context.

## Config planes

- A config-plane context carries no secrets document (`Arc<Secrets>`). The identity plane hashes a declared OAuth client's secret through `IdentityClientSecrets`, which the identity member provides from the sealed secret store and which resolves custom secrets only; a client `secret_key` naming a built-in secret (a signing key, a database URL, a provider key) is refused as absent. An install plane that read `Arc<Secrets>` provides its own narrow handle from `Arc<dyn SecretStore>` in a provide fn instead.
- `ConfigPlane::requires` is a required method: a plane names the state types it cannot read or write without, as jobs do. The reconciler reports a plane whose requirement is unmet as `unavailable` (scheduler migration 010 admits the value in `config_plane_state.outcome`) without reading it, and a diff, export or apply of it fails with `ConfigPlaneError::UnmetRequirement`. `PlaneSnapshot` is a type of its own instead of an alias for `BTreeMap<String, String>`. `PlaneReport.error: Option<String>` is replaced by the typed `failure: Option<PlaneFailure>`, rendered only at the CLI, the probe and `config_plane_state.last_error`. Migrate an install plane by adding `fn requires(&self) -> Vec<StateRequirement>`.

## Content

- The content hooks are `systemprompt_content::contract::ContentSlot`, whose builder takes a `Factory` per hook, built into `ContentHooks`. `execute_content_ingestion` takes `&ContentHooks`, `PrerenderEnv` carries `hooks` and `state` instead of an `ExtensionContext`, and `execute_copy_extension_assets` takes the declared assets (`declared_assets(&BuiltState, &dyn AssetPaths)`). A profile that disables `content` refuses `generator`. The Markdown alternate of a content item is `GET /api/v1/content/{source_id}/{slug}/{suffix}`, answering 404 unless content negotiation is enabled and the suffix matches. Migrate content hooks to `ContentSlot`.

## Coordination

- `LeaseRepository::release` takes the held `Lease` and deletes the row only while it still carries that fencing token, returning `CoordinationError::Fenced` otherwise. The process lease supervisor renews through `renew(&Lease, ttl)`; a fenced renew stops the local process and writes nothing.

## Data access

- A user route reads an agent run, an upload session, an issue report or a tool execution through the caller: `find_owned_run`, `DocumentUploadRepository::find_owned`, `IssueReportRepository::find_reported_by` and `ToolUsageRepository::find_visible` put the owner predicate in SQL, so another user's id answers exactly as an unknown one. `TaskRepository::list_tasks` pages by keyset (`created_at DESC, task_id DESC`) and returns a `KeysetPage`; A2A `ListTasks` page tokens are opaque keyset cursors, so a page read after new tasks were created neither repeats nor skips a row. `KeysetCursor` moves from `systemprompt_models::notifications` to `systemprompt_models::api` and is generic over its id type (default `Uuid`, today's notification wire form). The new `lint-owner-witness` gate refuses an id-only read named from a user-policy handler.

## Database

- The schema installer runs over the admitted composition (`install_admitted_schemas`, or `install_schema_members` for an explicit member set) and records the owner of every table it creates in `schema_table_owners` (migration 010) and each member's purge declarations in `schema_purge_records` (migration 011). A member declaring a table recorded to another member is refused before any DDL, including a member the profile disables or the install holds back, a core member included, so a disabled member's recorded tables cannot be adopted; the record, the rows and the absent member's purge record stay. Each install also records the owner of every index, routine, view, materialized view, sequence, type, domain and trigger in `schema_object_owners` (migration 012), so a disabled member keeps its objects as it keeps its tables. Before any DDL the installer judges each pending migration, and every statement of an install member's declarative schema by the same path, against ownership, tables and objects ranked alike (the live record, then a core member before an install member, then a declarative schema before a migration, then composition order; a held-back member claims but is not judged; an install-standing record whose owner is admitted and not held back is no claim, and is deleted after the install's DDL, when a core member's SQL creates the same table or object, the owner's own create of it being refused; a record of a held-back or disabled owner always stands, and a core member's create of its table or object is refused; an object record is deleted when its admitted owner's SQL no longer creates the object, unless the owner has a tombstoned migration and the object is not a trigger on a table it retires): a `CREATE TABLE`, including `CREATE TABLE ... AS` and `SELECT ... INTO`, of another member's table is refused (`MigrationOwnershipError::SharedTable`); an `ALTER TABLE` (including `SET SCHEMA` and `ENABLE ROW LEVEL SECURITY`), `DROP TABLE`, `TRUNCATE`, `RENAME`, `CREATE RULE`, `CREATE POLICY`, `ALTER POLICY`, `DROP POLICY|RULE ... ON`, `GRANT` or `REVOKE` on another member's table, also inside a `sql` routine body the migration defines or a rule's actions, and an `INHERITS`, `PARTITION OF`, `INHERIT`, `NO INHERIT`, `ATTACH PARTITION` or `DETACH PARTITION` naming it, is refused (`MigrationOwnershipError::ForeignTable`), while `LIKE` and foreign-key `REFERENCES` only read it; `DROP SCHEMA`, `ALTER SCHEMA ... RENAME`, `GRANT`/`REVOKE ... ON SCHEMA` and `GRANT ... ON ALL ... IN SCHEMA` over `public` or a schema holding another member's objects, and `ALTER TABLE ALL IN TABLESPACE`, are refused (`MigrationOwnershipError::SchemaLevel`); an `INSERT`, `UPDATE`, `DELETE`, `MERGE` or `COPY` into a kernel ledger table is refused (`MigrationOwnershipError::LedgerWrite`), except a `DELETE` of the `extension_migrations` rows of ids no member or record holds, and any other statement on a ledger, a trigger, index, rule or policy included, is refused for every member but the core `database` member, as is an install member's view, materialized view or rule that reads a ledger; an install-standing member never holds a core-standing claim under the same id. An index, routine, view, materialized view, sequence, type, domain or trigger is owned by the first member whose SQL creates it; for an install member, a create of another member's object (including `CREATE OR REPLACE`, `IF NOT EXISTS` and `CREATE OR REPLACE TRIGGER`) and an `ALTER` (including `OWNER TO`, type attribute and domain constraint alters), `RENAME`, drop (with or without `IF EXISTS`), move, `GRANT` or `REVOKE` of it are refused whatever statement form names it, in a migration or a declarative schema, an `ALTER TABLE` of a view, sequence or index included (`MigrationOwnershipError::ForeignObject`), so naming a peer's object in a create never makes it the install's own; and a `CALL`, `EXECUTE`, `COPY` from a file or program, unparseable `sql` routine body or unclassified statement kind, whatever it names, is refused (`MigrationOwnershipError::Unreadable`). A `DO` block (once per migration, naming the member and the migration), `CREATE EXTENSION`, `CREATE INDEX` on another member's table, a new trigger or a drop of the member's own trigger on another member's table (not a kernel ledger), non-`sql` routines, a routine call in a top-level `SELECT` or a data write, an unknown index drop, every `CASCADE` drop of an install member and a core member's `CASCADE` drop of an object it does not own are logged as unjudged. A member's `retirements()` may name a table (`DROP TABLE IF EXISTS`): the statement is not executed, the table is no longer the member's by its migrations or its record unless its declarative schema still creates it, and the install releases the member's record of it; `managed_resources` retires the five tables its migration 016 drops inside a `DO` block, so an install's drop of `managed_invocation_attributions` (still present where a consumer view read it) is admitted. A table no member owns, including one its owner retired, may be mutated or declared by any member. An install whose pending migrations or declarative schema hold a refused kind fails its schema install until the SQL is replaced. A migration recorded as applied, and a fresh database's stamped migrations, are not judged; an install member's declarative schema is judged on every full install (a settled install runs no DDL and judges nothing), and one that does not parse is refused (`MigrationOwnershipError::Parse`). `infra db doctor` reports tables and migration ledgers of a member outside the composition as `absent_member_tables` and `absent_member_ledgers` rather than as undeclared residue. The schema fingerprint no longer includes the disabled list, so a profile with disabled extensions runs one full schema install on its next boot. Upgrade: run one install with every member enabled so table ownership and purge declarations are recorded for each member. When a core release newly creates a table or object a disabled or held-back install member has recorded, every full install is refused until that member is enabled for one install, which moves the record to core.
- `infra db migrate` exits non-zero when it holds a member back because the database records migrations for that member which the binary does not know. The error names each held-back member with those migrations and lists the members it installed; a held-back member is never reported as installed, and none of its schema is applied. Operator action: run the release that wrote those migrations, or add a tombstone for a migration no release ships, then migrate again.

## Error types

- Error enums in the domain, app and infra crates no longer carry a bare `String` payload: a rendered cause is a `#[source]` and a message is typed fields or a typed id (`OauthError::{Validation, InvalidClientMetadata}` wrap `ValidationError`/`ClientMetadataError`; `McpError` gains `SchemaViolation`, `RegistryViolation`, `ConfigurationIssue`, `AuthRequirement`). Variants no production code built are removed (`OauthError::{TokenNotFound, CodeNotFound, PkceMismatch, Unauthorized}`, `McpError::Manifest`, `ContentError::{ContentNotFound, LinkNotFound, InvalidRequest}`, `UserError::{InvalidStatus, InvalidRole}`, `TemplateError::NotFound`). Migrate by updating constructions and exhaustive matches; Display texts are unchanged except `McpRegistry`'s not-found message, which now names the server alone.
- `AnalyticsError::InvalidArgument` is a struct variant `{ field, reason }`, built with `AnalyticsError::invalid_argument(field, reason)`; `ManagedError::Invalid` and `ManagedError::Conflict` are struct variants carrying `reason: &'static str`. Migrate each match and constructor to the struct form.

## Extensions

- `Extension` is `metadata()` plus one `contribute(&mut Contributions)`: a member declares its schemas, migrations, seeds, routes (`RouteSet`), gateway routes, commands, jobs, retention, projections, run origins, provided and required state, slots, readiness checks, diagnostics, metrics, gateway guards, site auth, configs and assets through `Contributions`, and the composition admits them before any is built. The defaulted hooks (`schemas`, `router`, `routers`, `jobs`, `provide`, `requires`, `diagnostics`, `metrics`, `runner_services`, the content, gateway, governance, notification, brain, files, marketplace and MCP hooks), `ExtensionRegistry`, `ExtensionRouter`, `ExtensionRouterConfig`, `StateBuilder` and `ExtensionContext::{get_extension, has_extension}` are removed. The `register_extension!`, `submit_job!`, `register_retention_purge!`, `register_retention_sweep!`, `register_retention_hold!`, `register_job_run_scope!`, `register_gateway_guard!`, `register_notification_*!`, `register_resource_visibility!`, `register_brain_*!`, `register_document_codec!` and `register_document_template_provider!` macros, their registration types and `registered_*` readers are removed, and the `inventory` dependency is gone. Contract types move: `SubjectAttributeProvider`, `SubjectDimension`, `SubjectAttributeError` and `RESERVED_SUBJECT_DIMENSIONS` to `systemprompt_traits::authz`; `GovernancePolicy` (without `secret_scanner`), `Decision`, `EntityKind` and `RuleType` to `systemprompt_provider_contracts::governance`; `ProjectionDrain` to `systemprompt_extension`; `RunOrigin` and the subscribe-only `AnalyticsSubscription` to `systemprompt_traits`; the capability HTTP error, `capability_error_response!` and content negotiation to `systemprompt_extension::router`; the CLI command traits, descriptor, settings, output and `Prompter` to `systemprompt_extension::cli`. Migrate by moving each hook body into `contribute` and importing the moved types from their new paths.
- Capability seams are slots with one owner: a member contributes to a slot its owning domain opens, and the kernel builds it once. Two slots building one type, or a slot building a type another member provides, are refused (`DuplicateProvider`); an install slot value cannot meet a core requirement (`InstallSubstitution`) or replace the gateway safety scanners, authz hooks, route selectors, overrides or the audience set; slot values are inserted through the duplicate-checked provide. A failing contributed seam refuses the slot build (`SlotError::Entry`, `SlotError::Refused`) instead of being skipped, and a second artifact theme, two renderers for one artifact type, a second role directory, a second agent access policy, a hosted toolset id no member contributes, or an outbound adapter or safety scanner named like a built-in refuse the composition. The `register_*!`/`submit_*!` macros of these seams are removed. Migrate each registration to the owning crate's `contract` slot.
- `ContextKind` gains `HandlerResolved` and `AuthzPolicy` gains `handler_verified(HandlerVerifier)`, for core route groups that authenticate in their handlers or token gates; the pairing mounts no context middleware or gate and keeps the declared body limit, rate limit and layers. `ContextKind` stays exhaustive so a host match cannot fall through to a wildcard. Boot refuses any other pairing (`MountError::IncoherentHandlerVerification`), a member declaring either without holding the matching privileged shape, and a group-level body limit above 2 MiB that no privileged shape grants for that base path (`MountError::UnlistedBodyExemption`). Migrate exhaustive matches on `ContextKind` and `MountError` by adding the new arms.
- The `ExtensionContext` trait, `DynExtensionContext` and their prelude re-export are removed. Every value it handed out is a typed kernel seed: a job, runner service or config plane resolves `Arc<dyn FileStorage>`, `BackgroundTasks`, `InstanceId`, `ServicesView`, `DynInstanceRegistry`, `DynLeaseRepository` and `DynAdvisoryLocks` with `ctx.get::<T>()`; a core member's provide fn, factory or slot build reads those and the host-sealed seeds (`Arc<Config>`, `Arc<dyn SecretStore>`, `SystemAdmin`, `ActiveServicesRoot` and the rest) with `r.get::<T>()`. An install member's provide fns, factories and slot builds read only the host-sealed seeds `reserved::INSTALL_SEEDS` lists (`Arc<Config>` and `SystemAdmin`). A route set's state, core or install, reads no host-sealed seed: only open seeds and values its own member provides, and a sealed read there fails boot with `MissingDependency`.
- A job name has one owner: two admitted members contributing the same name, an install job named like a scheduler job included, are refused at composition (`CompositionError::DuplicateJob`) and when the kernel builds the schedule (`KernelError::DuplicateJob`), before any schedule row is written. Rename the install's job. The scheduler's kernel-job handles attach only to jobs whose admitted owner is the scheduler member with core standing.
- A gateway guard, a slot entry (an authz hook, a marketplace filter) and a subject provider are built before the kernel builds the subject provider set, so none of them can read `Arc<SubjectProviderSet>`; only `provide_after_governance` fns can. One that needs subject attributes holds `systemprompt_governance::authz::SubjectSourceCell` (`r.get::<SubjectSourceCell>()`), which the kernel binds to the set once the composition resolves; `SubjectSourceCell::get` withholds the set with `SubjectSourceError::NotReady` until then. An install subject provider for the reserved `role` dimension is refused (`SubjectProviderError::ReservedDimension`).
- The JWT signing keys are a sealed kernel seed: no job or runner-service context carries `SigningKeys`. A member that mints tokens builds a purpose-typed issuer from the sealed keys in its provide fn or runner-service factory (as the agent-runs runner service does for run credentials) and its runtime code reads that issuer.
- Owner reassignment is a contribution: each member whose tables key rows on a user declares its own reassignment with `Contributions::owner_reassignment`, and the kernel admits it only when every column it names is a plain identifier on a table the member's own schema creates (`KernelError::Reassignment`). An account merge runs the admitted reassignments in composition order; the kernel no longer holds a list of them.
- The configured-inventory refresh is reachable outside the marketplace member only as `DynInventoryPublisher` (`publish_latest` with the caller as the actor). `Arc<InventoryRefresher>` is no longer a provided value; the member's own `managed_inventory_refresh` job resolves it under a type private to `systemprompt-marketplace`.
- `systemprompt-models` links `rmcp` only with its new `mcp` feature. Without it, `ai::{AiProvider, DynAiProvider, AiResponse, StreamChunk, CallToolResult, ToolResultFormatter}`, the `ai::{provider_trait, response, tool_result_formatter}` modules and `mcp::{apps, client_profile, McpToolResultMetadata, ClientProfile}` are absent. Migrate by enabling `systemprompt-models/mcp` (or the facade's `mcp` or `ai` feature) in a crate that names them.

## Facade

- A binary is a composition: `systemprompt::reference().with(member).without::<Member>().run()` admits the members, drops every contribution of a member the profile disables before any provide fn, factory or slot build runs, and starts the CLI or server. `RuntimeBuilder` and `RuntimeError` are removed from the facade, and `systemprompt_cli::{run, run_process, run_process_with, run_with}` are replaced by `run_composed(build, declared, secrets, admit)`. An id in `extensions.disabled` that names no composed member, a disabled required member, a member requiring a disabled member and two members providing one type fail boot (`CompositionError`). External secrets sources are declared with `Composition::secrets_source`. Migrate an install `main` to `systemprompt::reference()` plus its own members and `run()`.
- The `files` and `managed_resources` members are required: the runtime assembles the document store and the marketplace authorization stage on every host, so a profile listing either in `extensions.disabled` is refused at boot (`CompositionError::RequiredDisabled`). Remove them from `extensions.disabled`. A second `Kernel::resolve` over one admitted composition is refused (`KernelError::AlreadyResolved`), and a schema install where the database is ahead of one member still counts that member as the owner of its tables.
- The facade's `slack`, `teams`, `agent-runs` and `notifications` features each link the capability's domain crate and its entry crate (`systemprompt-slack-entry`, `systemprompt-teams-entry`, `systemprompt-agent-runs-entry`, `systemprompt-notifications-entry`); `api` turns on each linked entry crate's `http` routes. The features no longer enable features of `systemprompt-api`, `systemprompt-cli` or `systemprompt-mcp-host`. `systemprompt::slack` and `systemprompt::teams` re-export both crates; `systemprompt::agent_runs::entry` and `systemprompt::notifications::entry` name the entry crates.
- The `systemprompt` binary is built from the facade with the `full` composition (`cargo build -p systemprompt --bin systemprompt --features full`, `cargo install systemprompt --features full`); `systemprompt-cli` is a library with no binary and no `full` feature. The facade's `cloud` feature links `systemprompt-cloud-entry`, `analytics` links `systemprompt-analytics-entry`, and the new `content` feature links `systemprompt-content` and `systemprompt-content-entry`; `api` turns on each linked entry crate's `http` routes and `cli` its commands; `core content popular`, an analytics report under the `core content` group, is registered only when both `analytics` and `content` are enabled; `full` implies all three. A binary built without a capability's feature has neither its routes nor its commands. Migrate an install binary by enabling `cloud`, `analytics` and `content` (or `full`) alongside `api`/`cli`, and by building `main` on `systemprompt::reference().run()`.
- The facade's `full` feature is removed; `reference` is the reference composition (every core capability, the API and the CLI; `slack` and `teams` stay opt-in) and admits the same members `full` did. The new `ai` feature carries `systemprompt-ai`. The supported compositions are `reference`, `reference` with `slack` and `teams`, `api`, `core` with `cli`, the gateway (`api`, `ai`), the minimal kernel (`core`, `database`) and `core`; CI builds each and boots the two that link the `systemprompt` binary, and any other feature combination is unsupported. Migrate by replacing `features = ["full"]` with `features = ["reference"]`.
- `systemprompt::api` re-exports only `ServicesRefresh`, `EarlyServer`, `bind_and_serve`, the context middlewares and extractor, the health and process-monitor types and `error`, not the whole of `systemprompt_api`. The document actor-scope middleware (`same_origin`, `scope`) is `systemprompt_files_entry::http::documents::actor_scope`. Migrate other `systemprompt::api::routes` paths to the member crate that serves the route, or to `systemprompt_api` directly.
- A requirement whose only provider is withheld because that provider's own dependency is absent is refused with `CompositionError::WithheldDependency`, which names the provider and the dependency it was withheld with; `CompositionError::DisabledDependency` means only that the provider itself is disabled in the profile. Migrate by adding the variant to exhaustive matches.

- The gateway accounting journal is an append-only, encrypted, group-committed segment log: concurrent requests share one fsync instead of several each. Receipts written by older releases in the per-file format are not replayed — drain a node (let it settle its pending receipts) before upgrading it.
- `GatewaySurfaceRoutes::consumer_catalog` is replaced by `managed_consumer: Option<ManagedConsumer>`, which builds the `marketplace-http` consumer routes from the marketplace route state; the API no longer depends on `systemprompt-marketplace`. Migrate by reading `ManagedConsumer::catalog`.

## Identifiers

- A provider tool use id is the typed `ToolUseId`: `AiContentPart::ToolResult` and `AiContentPart::tool_result`, the thought signature store (`ThoughtSignatureWrite`, `AiThoughtSignatureRepository::find`) and cache (`ThoughtSignatureCache::store`/`lookup`), the policy `AuditTarget`, the governance decision record and the agent run events (`RunEventPayload::ToolUse`/`ToolResult`, `RunEvent::tool_use_id`) take and return it. The serialised value is unchanged.

## Job contract

- `Job` gains `requires()` (types the job cannot run without; an unmet one refuses the scheduler start with `SchedulerError::UnmetRequirement`) and `missed_runs()` returning `MissedRunPolicy` (`Skip` by default, `RunOnce`, `CatchUp { max }`). `RunnerService` gains `requires()`. `StateRequirement` moves to `systemprompt-provider-contracts` (still exported by `systemprompt-extension`). A job context keeps the sealed values its own member provided (`JobContext::for_member`) and withholds every other sealed value.

## Lease fencing

- Every instance lease carries a monotonic `FencingToken`: a claim that changes the owner stamps a strictly larger token, and `LeaseRepository::renew` extends a lease only while it still carries the holder's token, otherwise changing nothing and returning `CoordinationError::Fenced`. Database migration 016 adds `instance_leases.fencing_token`. Implementors of `LeaseRepository` add `renew`; code building `Lease` sets `fencing_token`.

## Loader errors

- `LoaderError::SchemaInstallationFailed`, `MigrationFailed` and `InitializationFailed` are removed in favour of the sourced `SchemaFault`, `MigrationFault` and `MissingProvider`, and `ConfigValidationFailed` carries an `ExtensionConfigError`. Migrate by updating exhaustive matches.

## Log files

- `find_log_file` returns a `LogFile` already opened beneath the logs root (`path_confine::open_within` checks the held handle is the confined file), and `read_log_lines` reads through it, so locating and opening a log are one step.

## MCP

- Every hosted MCP server answers its own loopback port only to a request carrying the API proxy's hop token, whatever its `oauth.required`; a direct request without one is refused with 401. Health checks of a hosted server (`plugins mcp validate`, the orchestrator and the agent tool provider) probe the port only and report `auth_required` without a tool count. A proxied MCP request that names a context (`x-context-id`) is refused with 403 `context_not_owned` unless the caller the proxy verified owns that context.
- The hosted document and issue toolsets are built by `DocumentsMcpTools::hosted` and `IssuesMcpTools::hosted` from the host's kernel state; `DocumentsMcpError` and `IssuesMcpError` move to `systemprompt_documents::mcp` and `systemprompt_issues::mcp` and gain `MissingConfig`, and `HostContext::{documents, files_config}` are removed. `systemprompt-mcp-host` no longer depends on `systemprompt-files`.
- `UiRendererRegistration` is removed with `register_ui_renderer!` and `create_default_registry`: a member contributes a renderer through `systemprompt_mcp::contract::UiSlot`, and an entry for an artifact type that has a built-in renderer replaces it in every process that admits the member. Migrate each `register_ui_renderer!` or `inventory::submit!` of a `UiRendererRegistration` to a `UiSlot` entry in the member's `contribute`.

## Marketplace

- The `marketplace-http` consumer routes (`/api/v1/consumer-devices/enrollment`, the consumer bundle, receipt and session-binding routes) are mounted only when `gateway-http` is admitted, because the managed consumer they are built from is the gateway surface's; a profile that disables `gateway-http` but keeps `marketplace-http` answers them 404. Migrate by keeping `gateway-http` admitted wherever devices enrol.

Reads through the services tree (`GET /api/v1/marketplaces/{id}.yaml`, `core skills list|show`, `core plugins show|validate|generate`) refuse a path that resolves outside its root, a skill `file` outside the skill's directory, a script `source` outside the plugin's directory and a script `name` that is not one path segment; `plugins mcp logs` refuses a server name that is not one path segment. Migrate by renaming any skill, plugin or marketplace directory whose id fails these rules.
- `ManifestService::seal` is removed; manifests are sealed by the gateway's manifest signer.
- `render_marketplace_list` returns the typed `MarketplaceListView` instead of a `serde_json::Value`; its serialised body is unchanged.

## Marketplace routes

- The `/api/v1/marketplace` routes are contributed by the `marketplace-http` member (`systemprompt-marketplace-entry`, feature `http`) instead of being mounted by the API server; a profile that disables `marketplace-http` answers 404 on them. The group is now rate-limited under the `marketplace` scope with the `content` budget, and the plugin-file and catalogue routes build the API external URL from the runtime `Config`. `systemprompt_api::routes::marketplace` is removed.

A per-user marketplace filter is contributed to the `MarketplaceSlot` by a member.

## Messaging

- The Slack and Teams inbound routes are declared by the `slack` and `teams` extensions, which now live in `systemprompt-slack-entry` and `systemprompt-teams-entry`; `systemprompt-api` and `systemprompt-cli` no longer have `slack` or `teams` features. The routes mount only in a binary that links the entry crates (the facade's `slack` and `teams` features, with `api` for the routes), only while the profile leaves the extension enabled (a disabled one answers 404), and on the `all` and `api` roles. A Slack app's `signing_secret_ref` and `bot_token_ref` and a Teams app's `app_password_ref` must name custom secrets; a reference naming a built-in platform secret is refused by services validation at startup. Migrate by enabling the facade's `slack` / `teams` features in place of `systemprompt-api/slack` / `systemprompt-api/teams`, and by moving any built-in secret a messaging app referenced to a custom secret.

## Notifications

- The notification routes are served by the `notifications-http` extension in the new `systemprompt-notifications-entry` crate: `/api/v1/notifications` (user gate) and `/api/v1/admin/notifications` (admin gate) are contributed route sets in the content-and-misc route group, and the bridge inbox `/v1/bridge/notifications*` is a gateway route set, keeping the gateway credential, the `bridge_notifications` rate-limit scope, the bearer window and the gateway access log. The `notifications` extension provides the producer `DynNotificationSink` and the `NotificationsServiceSlot` the host binds, and runs the delivery consumer as its runner service. A profile that disables `notifications-http` serves 404 on all three groups; one that disables `notifications` while `notifications-http` stays enabled, or while `brain` stays enabled, is refused at boot. Without a bound notification service the `documents_inbox` tool is not offered. `systemprompt-api` and `systemprompt-mcp-host` have no `notifications` feature, and `brain` no longer implies `notifications` in `systemprompt-api`, `systemprompt-mcp-host` or `systemprompt-cli`. Migrate by enabling the facade's `notifications` feature, and by disabling `notifications-http` rather than `notifications` to switch off the routes alone.
- `notifications::NotificationEvent` gains `actor_is_system: bool`; `NotificationEvent::with_actor_is_system(true)` marks an event produced on the platform's own schedule (a scheduled job), whose `actor` is the account it is attributed to, and that account is then kept among the recipients, where a person's own action never notifies them. Routing reads the flag only: it is not stored on the notification and no API or SDK field carries it. An event serialised without the field decodes as `false`. Migrate a struct literal by setting `actor_is_system: false`; `NotificationEvent::new` already does.
- The documents MCP server reaches a user's notification feed through the `NotificationInbox` seam (`systemprompt_extension::{NotificationInbox, DynNotificationInbox, InboxError}`) that the `notifications` member provides, so `documents_inbox` is offered whenever that member is admitted and `systemprompt-documents` has no `notifications` feature. `FeedQuery` and `MarkReadOutcome` move to `systemprompt_models::notifications`. Migrate by importing them from there and passing a `DynNotificationInbox` to `DocumentsMcpConfig::notifications`.
- `NotificationAudienceResolver::dimensions` is a required method: it names every custom `Dimension` kind the resolver answers. An install resolver is consulted only for the kinds it declares, and two resolvers declaring the same kind refuse the audience set. Migrate by returning the dimension kinds the resolver handles, or `&[]` for a resolver that answers none.

## Observability

- A build without the `otel` feature refuses to boot when the profile sets `observability.otlp`: startup validation reports `observability.otlp` with the collector endpoint and the missing `otel` feature (`systemprompt_logging::OtlpExportUnavailable`), where it used to start and drop every log record and audit span. Migrate by building with the facade's `otel` feature, or by removing the block.
- OTLP export is live: with `observability.otlp` set and the `otel` feature built in, the server ships its own `tracing` pipeline — every persisted log entry as a log record and every span under a platform trace as a span — through a bounded queue to the collector, counting what it drops in `otlp_export_dropped_total{signal}`. The `otlp_export` replay job and its `otlp_export_state` table (dropped by migration) are removed; the audit tables stay the durable record. `batch_seconds` is now the longest an item waits before its batch ships.

## Overload

- Admission control is on by default and decided outside every other layer: `server.max_in_flight` defaults to 4096 in-flight requests per replica, each counted until its response body is read to the end or dropped (an explicit `null` is no ceiling), and the shed layer is the outermost layer of the API router, so a saturated replica answers `503` with `Retry-After: 1` before CORS, sessions, authentication, rate limits or body parsing. Migrate by setting `server.max_in_flight` to the replica's measured capacity, or `null` to keep queueing.

## Resilience

- The resilience primitives (`ResilienceGuard`, `CircuitBreaker`, `Bulkhead`, `retry_async`, `guarded_stream`, `Outcome`) move from `systemprompt_database::resilience` to `systemprompt_storage::resilience`. Migrate by changing the import path.

## Routes

- The MCP tool-execution lookup `GET /api/v1/mcp/executions/{id}` is built by the `mcp-http` member's `McpSurface` over a ledger the member builds; the API keeps its declaration (authenticated, a user context, the `mcp` rate scope). With `mcp-http` disabled, or no MCP artifact ingest admitted, neither the lookup nor the MCP proxy is mounted (404).
- The services-tree sync routes under `/api/v1/sync` are built by the `cloud` member's `SyncSurface`; the API keeps their declaration (service callers only, a user request context). The `cloud` member is admitted whenever the `cloud` feature is on; with it disabled the routes are not mounted (404). `systemprompt_api::routes::{sync, sync_router}` are removed.

## Runtime

- `AppContext` is built from the admitted composition over a resolved `Kernel`: `AppContext::{new, builder}(boot, admitted)`, `AppContextBuilder::new(boot, admitted)` (no `with_extensions`), `from_parts(planes, kernel, admitted)` over a `ContextPlanes { data, cfg, plugins, subsystems }`, `AppContext::{kernel, admitted}`. `base_kernel_state(KernelSeed)` and `kernel_state(ApiKernelSeed)` seed the instance id, runtime config, services view and root, secret store, system admin, event router, escalation mode, brain profile and document handles; `Kernel::resolve` builds slots, then checks requirements. `session_store()` and `brain()` return `Option`, `load_governance()` returns `RuntimeResult`, and `extension_registry`, `analytics_service`, `analytics_repositories`, `session_usage` and `Plugins::extension_registry` are removed. Child hosts boot with `HostKernel::boot(lookup, AdmitFn) -> HostParts`. Migrate by building the context from the admitted composition and reading member-provided values from `kernel().state()`.
- `AppContext` exposes only `kernel()`, `admitted()` and its constructors. Every other host value (runtime `Config`, `DbPool`, `BootContext`, platform repositories, governance and services watches, event bridge, shutdown request, signing keys, token authority, …) is a typed seed read with `ctx.kernel().state().get::<T>()`. The seeds the context builds are sealed and their types reserved before members resolve; a kernel missing a host seed refuses `AppContext::from_parts` with `RuntimeError::Missing`. `from_parts` takes the `Kernel` by value and `ContextPlanes` carries only context-built values. `config_plane_set`, `reload_governance` and `load_content_config` are free functions. `SchedulerService::new` and `JobExecutionService::new` return a `Result`.
- `AppContext` has no per-value accessors (`db_pool`, `config`, `secrets`, `app_paths`, `profile` and the repository and service accessors): each value is a typed entry of the resolved kernel state, read with `ctx.kernel().state().get::<T>()` (for example `DbPool` or `Arc<Config>`), and a member reads it from the `Resolved` its provide fn, factory or route set is handed. `AppContext::new` takes the admitted composition. Migrate a standalone tool that needs only the database to `DatabaseContext::from_url` and `DatabaseContext::db_pool`.

## Scheduler

- capability jobs are exported by their owning crates: `BehavioralAnalysisJob`, `MaliciousIpBlacklistJob`, `GhostSessionCleanupJob`, `NoJsCleanupJob`, `BackfillSessionGeoJob` by `systemprompt-analytics`; `UsageAnomalyScanJob`, `ThoughtSignatureCleanupJob` and `AiRequestToolFlagRollupJob` by `systemprompt-ai`; `CleanupEmptyContextsJob`, `UserContextCountersRollupJob` and `EmptyContextRepository` by `systemprompt-agent`; `ToolRowFactsRollupJob` by `systemprompt-mcp`. `repository::{AnalyticsRepository, SecurityRepository, IpSessionRecord}` and `SchedulerRepository::{cleanup_empty_contexts, count_empty_contexts}` are removed, `SchedulerError` loses `Analytics`, `Managed` and `Mcp` and gains `DuplicateRetentionPurge` and `Extensions`, and `JobExecutionService::new` takes the `AdmittedSchedule`. Job names, schedules and parameters are unchanged. Migrate by importing each job from its owner.
- The scheduler runs the jobs, retention purges, sweeps, holds and job-run scopes of the admitted members, read from `AdmittedSchedule`; `SchedulerService::new`, `JobExecutionService::new`, `JobPruneService::new`, `unknown_job_names` and `unlisted_job_names` take it, and `EnabledExtensions` is removed. A scheduler config naming a job of a disabled or absent member is refused at validation, `admin config validate` reports it as not contributed, and `infra jobs prune` treats its row as prunable. Migrate by contributing jobs with `Contributions::job` and passing the kernel's `AdmittedSchedule`.
- a job is contributed only with `Contributions::job`; `infra jobs list` and `infra jobs show` report each job's `owner`, and a job of a disabled member is reported as unregistered.
- `Job::configured` receives no profile: its deployment map holds only the scheduler member's typed facts for its own jobs. A member job that needs a deployment fact reads a value its own member provides from its execution context.

## Schema installer

- `install_admitted_schemas`, `install_schema_members`, `MigrationService::assess_freshness`, `schema_currency`, `audit_schema_residue` and the table/column validators take the target schema as a typed `SchemaName`; a real install passes `SchemaName::public()`.

## Security

- An install route may not reach a reserved path: every route's full path, parameter, catch-all and `service` prefix is checked at admission and re-checked at mount against `RESERVED_PATHS` (MCP proxy, gateway `/v1` and `/api/public/gateway`, well-known, discovery, probes, `/`, `/api/v1/core`, documents, uploads, issues, brain, notifications, content `/r`, analytics `/track`), each owned by a `CoreId` with a `ReservedReach` (`Prefix`, `Subtree`, `Exact`). An install has no root fallback (`service("/")`, `/{*path}` and `/{slug}` are refused), and one opaque `service` cannot cover all of `/api/public`. `RouteSetBuilder::service` nests one opaque service under a literal prefix, recorded as one `ANY` route that conflicts with every route the prefix covers. Migrate a fallback route to an explicit prefix under the member's base.
- `gateway.bridge_releases.token_secret` must name a custom secret: a built-in name (`signing_key_pem`, `oauth_at_rest_pepper`, the database URLs, the provider keys including `github`) is refused when the services config is validated. The bridge release source never reads a built-in secret, and the bridge settings view answers whether a custom secret or a provider key is configured but never for a signing key, the pepper or a database URL. Migrate by moving the token to a custom secret and naming it.
- The API no longer installs the whole runtime `Config` on every router. Each route carries an `EdgeConfigView` instead (the public URL, the advertised URL and the trusted proxies, the three facts `ClientIp`, `RequestBaseUrl` and the document routes' same-origin check read), and the OAuth routers carry the `IdentityConfigView` their handlers read. A member or install handler that extracted `Extension<Arc<Config>>` is refused `500`. Migrate by extracting `Extension<Arc<EdgeConfigView>>` for those facts, or by reading the value the member's provide is given.
- An owner reassignment is a declaration, not code: a member declares each user-keyed column an account merge moves as `OwnerReassignment { table, column, action }` (`ReassignAction::Update { touch, keep_target_on }`, `Delete { predicate }` or `ReplaceInArray`). Admission refuses a declaration over a table the member's schema does not create or naming anything that is not a plain identifier, and the merge renders each admitted declaration into its statement from quoted identifiers, so the table a declaration names is the table its statement touches. Every reassignment of a merge runs with the users-owned half (sessions, the governance record, the source delete) in one transaction, so a failure part-way leaves no half-merged account. Migrate a factory-built reassignment to one declaration per column.
- An install member reads only the secrets it declares: it declares each custom secret it reads with `Contributions::secret(SecretName)` and reads it through `Resolved::secrets()` (a `DeclaredSecrets`) in its provide fns, factories and slot builds; a route set's or a command's resolution reads none. Admission refuses, with `KernelError::ReservedSecret`, a declared name that any core member, the profile or the platform references: every Slack and Teams app ref, every agent and MCP server custom-secret grant, the catalog credentials' platform secrets, the gateway bridge-release token secret, the OIDC `client_secret_key`, every identity client's `secret_key`, the Git-source credential namespace (`GIT_SOURCE__…`), the pinned platform keys (`PINNED_SECRET_KEYS`, which now also back the refusal) and `licence_signing_secret`, compared without regard to ASCII case. The references are consulted again on every read, so a name a services reload starts to reference is refused from then on. What an install changes: add one `c.secret(SecretName::new("<name>"))` per custom secret it reads, replace `r.get::<Arc<dyn SecretStore>>()?.secret(name)` with `r.secrets()?.secret(name)`, and rename any secret whose name a core member references. The Slack and Teams members build their secret reads over the sealed store in their own provide fns.
- The runtime `Config` no longer carries the GitHub token, so an install member that reads `Config` cannot reach it. The token is held only in the sealed secrets document (`Secrets::github`), and `profile show` no longer lists it.
- A member reads a custom secret only when the profile grants it: `extensions.secrets` maps a member id to exact names and `prefix_*` patterns, matched byte-exactly. A declaration no grant covers fails boot with `KernelError::UngrantedSecret`; an unknown member id in `extensions.secrets` fails boot with `CompositionError::UnknownSecretGrant`. A name the platform references (pinned keys, `licence_signing_secret`, `mcp_credential_broker_secret`, and every secret field of the profile and services config, found by walking their serialized form) stays refused when granted. Migrate by adding `extensions: { secrets: { <member>: [<names>] } }` to every profile whose installs declare secrets.
- An install member's provide fns, factories, slot entries and governance factories (gateway guards, policies, subject providers, audience resolvers, runner services) resolve with its admitted standing: they read only the host-sealed seeds the closed table `reserved::INSTALL_SEEDS` lists — `Arc<Config>` and `SystemAdmin` — and never a value another member provided sealed. Every other host-sealed seed (the secret store, the secret lookup, the connector token cache, the signing keys, the spawner, the child secret environment, the messaging dispatcher, the agent dispatch, the event router, the services root, the profile path, the bundle sources, the owner reassignments) is withheld with the `MissingDependency` an absent type gets, so the resolution fails with `KernelError::Provide` (or `Slot`, `GatewayGuard`, `SubjectProvider`, `Policies`) at boot. An install reads the custom secrets it declares through `Resolved::secrets()` instead of `Arc<dyn SecretStore>`, and replaces every other sealed read with a narrow value a core member provides. Core members are not narrowed. Rescoping a resolution never widens it.
- No route set's state reads a host-sealed seed, whatever its owner's standing: `Resolved::__route_scoped` withholds every host-sealed seed for core and install route sets alike. The content, marketplace, agent-runs, Slack and Teams route sets read values their own member builds in a provide fn instead: `ContentHttpSettings` (the external URL and content negotiation), `MarketplaceHttpSettings` (the external URL and the system admin's id), `Arc<A2aRunnerConfig>` (the run layouts), and the sealed `SlackSecrets` / `TeamsSecrets` (an app's signing secret, bot token or password by the custom-secret refs its config names). Mounted policies, context kinds and refusals are unchanged.
- The gateway's inference, token-count, telemetry and personal-credential routes move from `systemprompt-api` into the `gateway-http` member (`systemprompt-gateway-entry`), contributed as a `GatewaySurface` the API mounts under the unchanged gateway layering. Their route state is resolved scoped to `gateway-http`: callers are verified through the request authenticator, and the engines, at-rest material, session mint and personal credential view arrive only through their conferral rows. Disabling `gateway-http` unmounts them; disabling `ai` unmounts only the personal-credential routes.
- The document store and the issue reports leave `systemprompt-runtime`: the `documents` member (`systemprompt-documents`) builds the store from the resolved kernel state, binds the `DocumentsHandlesSlot` it provides and confers two narrow token views, `DocumentLinkTokens` on `files-http` and `DynDriveTokens` on `gateway-http`; the `issues` member (`systemprompt-issues`) carries the issue MCP tools and the `admin issues` commands. Its access checks decide through the host's late-bound authz hook, which denies until the host binds it. Migrate `systemprompt_runtime::documents` and `systemprompt_runtime::issues` paths to `systemprompt_documents` and `systemprompt_issues`, and `AppContext::documents()` to the `DocumentsHandlesSlot` in the kernel state.
- The document, folder, upload, public-link and issue handlers leave `systemprompt-api` for the `files-http` member (`systemprompt-files-entry`, `http` feature), which contributes them as a `FilesSurface` the API mount builds with the `files-http` route-scoped state. The API keeps their layering unchanged: the documents and uploads routers are protected by the user gate, wrapped in their download or upload token gate and mounted handler-verified with the `documents` rate limit outermost; folders, the public-link open and issues keep their policies, context kinds and rate scopes. With `files-http` disabled none of these routes is mounted. The handlers read the store cell, the `DocumentLinkTokens` view conferred on `files-http`, the member's own settings and repositories, and no host-sealed value.
- The chat-platform messaging dispatcher moves to the `agent-http` member: it is built in that member's provide fn from the host's sealed authz hook cell, signing keys, issuer and agent dispatch cell, provided sealed, and bound into the messaging cell by the kernel when the server builds its routes. With `agent-http` not admitted every Slack and Teams dispatch is refused. `systemprompt_api::services::messaging` is removed; `bind_dispatcher` and `DispatcherBindError` are `systemprompt_api::services::agent_dispatch::{bind_dispatchers, DispatcherBindError}`.
- The device-credential consumer routes under `/api/v1` are built by the `marketplace-http` member's `ManagedSurface`; the API keeps their protection (handler-verified by the managed device credential, the `consumer_evidence` 10/s limit) between the member's origin guard and contract normaliser. With `marketplace-http` disabled the routes are not mounted (404). `systemprompt_api::routes::managed` is removed.
- The bridge routes move out of `systemprompt-api`: the credential exchange (`/v1/gateway/auth/bridge/*`) is built by `identity-http`, and the bridge profile, manifest, plugin files, device enrolment, host preferences, usage, heartbeat, event stream, release feed, `/models` and the public session mint by `gateway-http`. Their route state holds no application context: the `gateway` member confers four narrow views on `gateway-http` (`gateway-manifest-signer`, `bridge-release-source`, `gateway-settings`, `bridge-event-stream`), and every handler verifies the bridge bearer through the kernel's request authenticator. `GatewayPrincipal` is stamped only by the API's gateway verifier, which now also fronts the bridge profile. A profile that disables `gateway-http` or `identity-http` serves none of their routes (404).
- The CLI's admin flows (`admin bootstrap`, `admin session login`, CLI session creation, `infra db assign-admin`) find, create and promote the platform admin through the `DynAdminBootstrap` view, built before any kernel state from the constructor a core-standing `users` member contributes (`Contributions::admin_bootstrap`). An install's constructor is never called. The view cannot demote, delete, ban, merge, list or update a user.
- Two kernel grants for the identity member's CLI commands: `SigningKeys` hands a command the kernel-held `DeploymentSigningKeys` handle (token key ids, stage/promote/rotate, the manifest public key and its rotation; never a private key, seed or secrets source, and no token minting), and `ConfigPlaneWriter(GrantedPlane::Identity)` confirms the identity plane accepts a write. The reserved CLI paths `admin users`, `admin keys` and `admin bridge` are held by `identity-http`; an install, or a core member on a path whose row does not list the grant, is refused either grant.
- The API's replica-shared per-user rate-limit window is read through the `DynRateLimitBuckets` seam the users member provides, accepted only from `users`. A kernel without it, or with windows another member provided, counts the same budget per replica in memory instead of running unlimited. `RateLimitState::new` takes a `DynRateLimitBuckets`; `RateLimitState::from_kernel` builds the state from kernel state.
- The JWT authorization checks (`AuthorizationService`, `validate_service_access`, `validate_required_audience`, `validate_any_audience`) are `systemprompt_security::jwt`'s, the token endpoint's advertised vocabulary is `systemprompt_oauth_issuance::AuthorizationServerVocabulary`, and the API no longer depends on `systemprompt-oauth`. The checks themselves are unchanged. Migrate by importing them from `systemprompt_security::jwt`.
- `SsoHookContext` carries `EdgeConfigView` instead of the runtime `Config`, and the session middleware holds its cookie policy; `SessionCookie::from_config` is removed (use `SessionCookie::for_external_url`).
- `RuleTypeError` moves from `systemprompt_models::authz` to `systemprompt_provider_contracts::governance` and is re-exported by `systemprompt_governance::authz`. `AccessScope` is defined in `systemprompt_provider_contracts::governance` and re-exported as `systemprompt_governance::policy::AccessScope`; `systemprompt_governance::policy::types` no longer re-exports it. Migrate by importing both from those paths.
- `authz::AuthzHookContext`, `discover_subject_providers`, `discover_authz_hook` and `discover_role_directory` are removed. The kernel builds the subject provider set from the providers members contribute with `Contributions::subject_attributes`, the authz hook from `contract::AuthzHookSlot` and the role directory from `contract::RoleDirectorySlot`. Migrate a caller that discovered providers to read `SubjectProviderSet` from the resolved kernel state.

## Shared error types

- Error enums in the shared crates carry typed fields or a `#[source]` instead of a bare `String`: `ServicesValidationError` variants carry a `ValidationSubject` and a reason (`PortConflict` its port and the two claimants), `FileStorageError::Validation` a `StorageValidation`, `ToolProviderError` gains `CircuitOpen`, `ConcurrencyLimit` and `TimedOut`, and identifier-bearing variants carry typed ids. ## Shutdown

- The connection drain lasts until the longest permitted stream can finish: `server.shutdown.longest_stream_secs` (default 600) extends the drain to `max(drain_grace_secs, longest_stream_secs)`, capped at 86 400 s, before open streams are ended with their terminal frame; `total_budget` includes it. The drain still ends as soon as the last request does. Migrate by raising the orchestrator's termination grace to the logged total budget, or lowering `longest_stream_secs`.

## Traits

- `SessionStore` gains `ip_session_counts` (the per-IP session counts the IP detectors classify, read by the users crate) and `ToolExecutionLookup` gains `contexts_with_executions`; `EmptyContextRepository::new` takes the tool-execution lookup. Migrate by implementing the two methods on custom stores.

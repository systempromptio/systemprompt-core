# Threat Model

STRIDE-style threat model for the systemprompt.io governance binary. Scope is the code in this repository plus the surrounding operational context of a typical self-hosted deployment. It does not cover threats against the customer's upstream AI providers or downstream consumers — those sit outside the trust boundary by design.

## 1. System Overview

systemprompt-core is a Rust library compiled into a deployment binary. It routes AI traffic, evaluates configured governance policies and writes audit records. PostgreSQL provides persistence; models, tools and enabled integrations have additional dependencies.

High-level data flow:

```
Developer / Agent
    │ HTTPS through an operator-managed TLS proxy
    ▼
┌──────────────────────────────────────────────┐
│ Entry Layer                                  │
│   crates/entry/api                           │
│   routing; multi-dialect inference surface:   │
│   /v1/messages, /v1/responses,                │
│   /v1/chat/completions, /v1/models            │
└──────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────┐
│ Security / Identity                          │
│   crates/infra/security                      │
│   OAuth2/OIDC w/ PKCE, JWT verification,     │
│   issuer checks, RBAC                        │
└──────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────┐
│ Governance Pipeline (Infra / App / Domain)   │
│   crates/infra/governance,                   │
│   crates/app/runtime, crates/domain/ai,      │
│   crates/domain/mcp, crates/domain/agent,    │
│   crates/domain/marketplace,                 │
```

## 2. Trust Boundaries

| # | Boundary | Inside | Outside |
|---|----------|--------|---------|
| TB1 | Network edge | customer VPC / cluster | developers, agents, CI jobs |
| TB2 | Process boundary | systemprompt binary | OS, Postgres, provider SDKs |
| TB3 | Secrets boundary | ciphertext on disk when the customer uses envelope encryption (KMS / Vault / sops); plaintext only in the binary's process memory after launch | the master key that opens the envelope — owned by the customer's key-management programme, never held by the binary |
| TB4 | Audit boundary | audit and log rows in the customer's PostgreSQL; append-only only where the operator restricts the role's grants | downstream SIEM / object store |
| TB5 | Provider egress | customer-controlled outbound HTTPS to providers | provider cloud |
| TB6 | Integration egress | outbound HTTPS to Slack, Microsoft Teams, external MCP servers, authz webhooks, and JWKS endpoints | third-party SaaS and customer-operated tool servers |
| TB7 | Document sharing | a document's owner and the subjects its grants name, resolved through the subject directory and the authz hook | every other authenticated user, bridge devices and agents acting for a user |

## 3. Assets

1. **Bearer credentials** — JWTs, OAuth tokens, refresh tokens. Short-lived; transient in memory during request handling.
2. **Provider API keys and the JWT signing key** — Anthropic, OpenAI, Gemini keys, plus the RSA private key that signs first-party tokens. Loaded from a profile-referenced secrets file or environment into process memory for the lifetime of the process.
3. **MCP allowlist configuration** — signed manifest of permitted tool servers (integrity is load-bearing).
4. **Audit and log events** — record of every governed interaction. The gateway audit trail stores request messages (prompt bodies) and can store response and wire payloads. Rows are not hash-chained or signed, so the trail is not tamper-evident; its integrity rests on database permissions.
5. **User / RBAC data** — who can call what, scoped by handler boundary.
6. **Prompt and response content** — may contain PHI, source code, or other regulated data. The gateway audit trail persists request messages; terminal receipts awaiting database settlement are held encrypted (ChaCha20-Poly1305 under `encryption_master_key`) in the node's data directory.
7. **Per-user external credentials** — bearer tokens banked for external MCP servers and resolved per-caller through the `external_auth` seam; the deployment's own credential is deliberately withheld from the upstream server.
8. **Governance decision record** — every authorization decision, including denials, written to `governance_decisions` with the actor, context, and delegation chain.
9. **Document content and sharing state** — revision bytes in the storage backend, the per-document plain-text index, grants, comments, proposals and the grant audit log (`document_grant_events`). Confidentiality is the grant model's; integrity is the content-addressed revision chain's.

## 4. STRIDE Analysis

Each threat is mapped to the component where it originates, the mitigation in code, and residual risk that remains after mitigation.

### 4.1 Spoofing

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| Forged JWT impersonating a user or service | `crates/infra/security/src/jwt/validate.rs`, `crates/infra/security/src/keys/` | All first-party token decoding funnels through a single primitive, `decode_rs256_claims`. It rejects any header whose `alg` is not `RS256` and any header carrying `crit` before an RS256 `Validation` is constructed — the JWT plane is RS256-only and there is no ES256/ES384/EdDSA acceptance path, so HS256, `alg: none` and algorithm confusion are structurally unrepresentable rather than merely filtered. A `kid` is **mandatory** and is resolved against the deployment's verification keyring (the active key, a staged key and every unexpired retired key) plus the JWKS sets fetched for each `profile.security.trusted_issuers` entry; an unknown `kid` fails closed. Every validation policy pins an issuer and a non-empty audience set; a policy with no audiences is rejected as `EmptyAudiencePolicy`, so an "accept any audience" configuration cannot be expressed. Per-surface isolation uses typed `JwtAudience` values and per-server audience checks in `crates/domain/mcp/src/middleware/rbac.rs`. `exp`/`nbf` are checked with a pinned 30-second leeway, session tokens have their `act` delegation chain depth-capped, and `user_type` is re-derived from `scope` with a disagreeing claim rejected. | Trust in the issuer's private-key custody. Customer IdPs that publish a JWKS can be federated via `trusted_issuers`. Signing-key rotation (`systemprompt admin keys stage`, `promote`, or `rotate` for a single replica) keeps the outgoing key verifying, and published in the JWKS, until an overlap ends — by default the longest lifetime of any token the key can have signed; every minted token kind is bounded by a profile value or a one-year ceiling. A replica learns a new key only on restart, so a multi-replica deployment stages, restarts every replica, promotes and restarts again. `--revoke` promotes with no overlap and drops every retired key, after which every outstanding token signed by an earlier key, including long-lived plugin tokens and bridge and CLI sessions, is rejected. These commands are classified irreversible and require operator confirmation. Where the signing key is also held in Vault or a GitOps repository, removing the old key from that store after `rotate --revoke` is a manual step. |
| OAuth authorisation code interception | `crates/domain/oauth/src/repository/oauth/auth_code/` | PKCE is **mandatory at authorize** — a missing `code_challenge` is an error and a minimum challenge length is enforced (`routes/oauth/endpoints/authorize/validation/mod.rs:130-140`), and requests without a challenge are rejected. Only `S256` is accepted; `plain` fails to parse into `PkceMethod`. Verification compares the SHA-256 of the verifier against the stored challenge in constant time via `subtle::ConstantTimeEq` (`auth_code/pkce.rs:41-44`), and every failure mode collapses to the same generic message so the endpoint is not an oracle. Codes are single-use (`used_at`), short-TTL (`expires_at`), and `redirect_uri` must match the original request by **exact string comparison** — no wildcard or prefix matching (`services/validation/redirect_uri.rs:8`). Replay of a used code revokes the entire refresh-token family. | At authorize, `redirect_uri` is validated only when supplied; otherwise the client's registered default applies (`authorize/validation/mod.rs:58-68`). OAuth values are peppered at rest (HMAC-SHA256 under `oauth_at_rest_pepper`) but carry no `pepper_version`, so rotating the pepper invalidates every stored row (`at_rest.rs:10-13`). Compromise of the authorising IdP itself cannot be prevented. |
| Provider response substitution | `crates/domain/ai` | TLS via the customer's trust store; response content-type and schema validation | Upstream provider compromise is outside the trust boundary. |
| MCP session hijack or replay | `crates/entry/api/src/services/proxy/` | On a server whose OAuth requirement is set, the proxy authenticates every request on its own bearer at the edge, including audience and required scopes; a session id is a correlation handle, never a credential. The `initialize` response that mints a session binds it to the server and the authenticated principal, and a later request naming that session from another principal or server is answered `404`, the same as an unknown session. | A server declared without an OAuth requirement accepts anonymous requests, and its sessions are bound to the server with no principal. Declare `oauth.required` on every server that serves user data. |
| Client-supplied identity headers believed by a backend | `crates/entry/api/src/services/proxy/service/outbound.rs` | The proxy owns every identity and context header a backend trusts. A managed MCP server receives only the protocol headers (`content-type`, `accept`, `mcp-session-id`, `mcp-protocol-version`, `last-event-id`) from the client plus the headers the proxy sets from the verified request context. An agent backend receives the client's headers with every proxy-owned name (`authorization`, `x-user-*`, `x-proxy-*`, the scope prefix, context, trace and owner-hop headers) removed before the proxy sets its own. | A backend reachable other than through the proxy sees no such filtering; keep backend listeners off untrusted networks. |
| Federated identity taking over an existing account | `crates/domain/users`, `crates/app/oauth-issuance` | A federated identity (SSO, token exchange, Slack) whose verified email is already owned by an account is refused unless the issuer's `link.link_by_email` is `true` (default `false`). Even then, the account is linked only when it is active, has a verified email, is neither a service account nor a bot, and holds no role other than `user`; an admin or otherwise privileged account is never linked. The link decision runs under transaction-scoped advisory locks on the external subject and the email, so concurrent first sign-ins cannot both link or provision. A linked account keeps its own roles; identity-provider roles are applied only to accounts the provider provisioned. | Enabling `link.link_by_email` trusts that issuer's email verification for ordinary accounts. |
| Bridge trusting an impostor gateway's signing key | `bin/bridge/src/gui_policy/trust.rs` | The bridge GUI never pins a gateway's manifest-signing key on first use by itself. It shows the SHA-256 fingerprint of the key exactly as `GET /v1/bridge/pubkey` serves it, and pins only when the user confirms that fingerprint for that gateway and the key served at confirmation still matches. An administrator prints the expected fingerprint with `systemprompt admin bridge signing-key-fingerprint` (the lowercase hex SHA-256 of the base64 `pubkey` that endpoint serves) and distributes it to users out of band. | The check is as strong as the user's comparison against an independently obtained fingerprint. |
| MCP server impersonation | `crates/domain/mcp`, `crates/infra/security/src/manifest_signing.rs` | Signed manifest allowlist; manifest signature verified at load using the deployment's Ed25519 key (`ed25519_dalek`) over canonical JSON. The `manifest_signing_secret_seed` (Ed25519, manifest plane) is distinct from the RS256 token signing key (JWT plane), and each rotates separately. | Manifest-signing key compromise rotates via `systemprompt admin bridge rotate-signing-key`, which is classified irreversible and requires operator confirmation; bridges then confirm the new key's fingerprint before trusting it. |

### 4.2 Tampering

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| SQL injection | `crates/infra/database`, all repositories | Request-path queries use `sqlx::query!`, `sqlx::query_as!`, `sqlx::query_scalar!` — compile-time verified against the live schema. This is **mechanically gated, not review-enforced**: `scripts/check-sqlx.sh` (run in CI as `just lint-sqlx`) fails the build on any non-macro `sqlx::query*(` call outside a small allowlist of admin/bootstrap paths. `format!`-constructed DDL exists only in those bootstrap paths, where parameters come from the operator's config file rather than user input. Transaction-scoped Postgres GUCs used by the scoping seam are injection-safe by construction — the key is validated against a custom-GUC grammar and both key and value are bound as parameters (`crates/infra/database/src/scope/provider.rs`). | Review the SQLx checks and results for the evaluated commit. |
| Audit / log tampering | `crates/app/gateway/src/audit`, `crates/infra/logging` | Gateway admission rows (request, messages, payload, route, findings, governance decisions) are written in one transaction before the upstream call; completion is recorded afterwards, and a receipt that cannot yet be settled is held encrypted on the node and retried. The audit trail is **not tamper-evident**: rows carry no hash chain or signature, so an alteration by a party with write access is not detectable from the data. Append-only discipline is an operator-provisioned control: the systemprompt DB role is granted `INSERT, SELECT` (not `UPDATE, DELETE`) on the audit/log tables. **No `GRANT` statements ship in the schema migrations** — the grant is applied by the operator per the deployment guide. The one shipped schema-level control is a BEFORE UPDATE trigger on `governance_decisions` that refuses row updates; DELETE on it stays grant-controlled for retention and erasure, and the table owner can disable the trigger. Other audit and log tables carry no immutability trigger; customers requiring defense-in-depth may add a BEFORE UPDATE/DELETE trigger (recommended DDL in the deployment guide). | Post-insertion DB-admin compromise is not addressed at the schema level and is not detectable from the rows — layered defense via role grants plus the optional trigger; export to a write-once store for tamper evidence. |
| Profile structure altered through an environment value | `crates/shared/manifest/src/env.rs` | `${VAR}` interpolation runs over the parsed YAML tree after base and overlay are merged, never over document text, and only string values are rewritten; a substituted value cannot add a key, end a value early or start a comment. Mapping keys are never interpolated. A profile about to run fails at boot on a variable that is unset or empty and has no `:-` default, naming the variable and the key path. | Whoever controls the process environment controls the values it supplies. |
| MCP allowlist tampering | `crates/domain/mcp`, `crates/infra/security/src/manifest_signing.rs` | Manifest loaded from signed source; Ed25519 signature verified at load using the deployment's `manifest_signing_secret_seed`; hot reload re-verifies. | Requires key-management discipline on the customer side. |
| Prompt/response modification in transit | entry | Operator-managed TLS termination in front of the API HTTP listener. | TLS downgrade protected by customer reverse-proxy config. |

### 4.3 Repudiation

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| User denies having issued a governed request | `crates/infra/events` | Every request is bound at entry to an authenticated identity; the audit row carries the JWT `sub`, request ID, timestamp, and full rule-evaluation trace. | Relies on the customer's IdP logs for the identity-to-human binding. |
| Tool invocation cannot be attributed | `crates/domain/mcp`, `crates/domain/agent` | A2A (agent-to-agent) `Task.contextId` + `Message.messageId` propagate through the call graph; audit events reference these IDs. | Customer must preserve audit retention for the forensic window. |

### 4.4 Information Disclosure

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| Secrets leaked via logs or error traces | `crates/infra/logging` | Structured tracing logs typed error values, not raw secret inputs; bearer tokens are stripped before request logging. | Third-party crate log output remains possible; the customer filters at the log shipper if required. |
| Configuration injection through an environment value | `crates/shared/manifest/src/env.rs`, `crates/shared/manifest/src/profile/layered.rs` | Profile `${VAR}` interpolation is structural: each layer is parsed as YAML first and only string values of the parsed tree are substituted, so a value containing `#`, `: `, a newline or braces cannot end a value, start a comment or add a key. The value enters the field as the field's schema type (a string field always receives text). A variable that is unset, with no `:-` default, fails the boot naming the variable and the key path instead of leaving the literal placeholder as configuration. | The operator controls the environment; the values themselves are trusted as configuration. |
| Provider API keys and JWT signing key exposed at rest | `crates/infra/config/src/bootstrap/secrets/`, `crates/shared/manifest/src/secrets.rs` | The binary does **not** perform symmetric at-rest encryption of secrets. Secrets are loaded from a profile-referenced JSON file or environment into process memory at startup. The expected deployment model is that the customer uses their existing envelope-encryption infrastructure (HashiCorp Vault, AWS/GCP/Azure KMS, sops + age, or equivalent) to protect the secrets file on disk and decrypt it into the binary's environment or a tmpfs-mounted file at launch. The master key never enters the binary — the customer's key-management programme governs it end-to-end. The deployment guide documents the supported patterns. | Filesystem permissions on the secrets file (0600, dedicated service account) are the fallback for deployments that do not use envelope encryption — acceptable only outside regulated contexts. |
| Audit data exfiltration via DB compromise | `crates/infra/database` | The systemprompt DB role is provisioned least-privilege (`INSERT, SELECT` on the `logs` and `analytics_events` tables; no `UPDATE`, `DELETE`); the deployment guide recommends a separate read-only role for SIEM export. The grant is operator-provisioned, not shipped in migrations. | Database-admin-level compromise remains high-impact — mitigated operationally (customer Postgres RBAC), not architecturally. A BEFORE UPDATE/DELETE trigger may be layered for defense-in-depth. |
| Server-side request forgery via configured or caller-influenced URLs | `crates/shared/models/src/net/`, individual HTTP clients | Parse-time validation checks schemes and literal addresses. The shared guarded client validates DNS results and redirect destinations. Trusted-host and loopback exceptions support configured local services. See [outbound egress controls](outbound-egress-controls.md). | Enforcement depends on the HTTP client used by each integration. Behind a forward proxy, destination filtering for hostnames is the proxy's job: the client still refuses blocked literals, `localhost` names and disallowed schemes, but cannot see what the proxy resolves a hostname to. Review trusted-host configuration and test destination and redirect policy with deployment egress controls. |
| Outbound telemetry to the vendor | whole binary | None is sent: no crash reporting, usage pings or update checks; every outbound connection is operator-configured. See [SECURITY.md § Telemetry](../../SECURITY.md#telemetry). | Operator-configured destinations (providers, OTLP collector, cloud profile, bridge release repository) are governed by egress policy, not by the binary. |
| Caller identity leaking to an upstream provider | `crates/app/gateway/src/service/` | The caller's own credential is **never** forwarded upstream — the gateway substitutes the deployment's provider key, resolved by name from the secrets store against the matched route (`service/resolve.rs`). `strip_caller_identity` (`service/stages/outbound.rs`) unconditionally removes `metadata.user_id` from the canonical request, and the passthrough lane does the same, so an end-user identifier cannot reach a provider the caller did not choose. Forwarded headers are an explicit allowlist. | Prompt content itself still crosses TB5 by design; that is the governed action, recorded in the audit trail. |
| Unscanned content reaching a provider or a client | `crates/app/gateway/src/service/stages/scanned.rs`, `crates/shared/wire/src/inspect.rs`, `crates/app/gateway/src/service/finalize/` | Request scanners read every string leaf of the body actually forwarded upstream, so content the inbound parser does not model is still inspected. Under an enforcing policy a request whose inspection surface is incomplete (the walk was cut short by its budget, or the body is not JSON) is refused rather than forwarded partly unread. A buffered response is scanned on the bytes the client would receive and can be refused before it is served. | Scanners inspect text: binary media (images, documents) is forwarded without text scanning. A streamed response is scanned once it completes, after its bytes have reached the client, so response findings on a stream are recorded, not blocked. |
| PHI / regulated content accidentally persisted | `crates/domain/ai` | Gateway audit paths persist request messages and can retain response and wire payloads in PostgreSQL. | Apply access, retention and deletion policies to request payload tables and backups. |
| A user-scoped organisational-memory fact reaching another user | `crates/domain/brain` | One rule, applied in Rust and in the working-set SQL view, decides which scope keys a fact carries: topic audiences widen project, group and org facts, never a user-scoped one, and the working-set view admits a user-scoped fact only under its owner's key. Search reads only facts reachable through the caller's keys and pages with an opaque cursor bound to its reader. | Visibility of project, group and org facts follows the topic audiences and memberships the deployment configures. |
| Cross-tenant data bleed | `crates/infra/governance/src/authz/`, repository queries, handler boundary | Isolation today rests on three mechanisms: per-`user_id` filtering in repository queries; the authz resolver, which is deny-overrides and treats a declared ruleset as authoritative and closed at each level of the parent chain, returning `UnknownEntity` rather than a generic deny for unregistered entities (`authz/resolver.rs:94-110`); and subject-keyed quota buckets. Handler-boundary RBAC is enforced for MCP in `crates/domain/mcp/src/middleware/rbac.rs`. | Core has no connection-scoping layer (no per-request Postgres settings are applied to a transaction) and **no RLS policies ship in any migration**, so core provides **no row-level tenant isolation**. Deployments requiring hard multi-tenant separation should run one instance per tenant. Test cross-tenant access across repository queries and configured integrations. |

### 4.5 Denial of Service

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| Request flood at entry | `crates/entry/api` | A default request body limit of 2 MiB is applied at the API edge (`crates/entry/api/src/services/server/builder.rs`), with explicit per-router limits where a surface needs a different size (agent and A2A, documents, Drive, uploads, managed consumer); raw body reads go through one bounded reader that refuses an oversized body with `413` before reading it. A per-IP limiter (`rate_limits.pre_auth_ip_per_second`) runs ahead of every authenticating layer, so a flood of forged or expired credentials is throttled before any token decode or revocation lookup. Per-route rate limiting and bot/ban controls are applied as further middleware. Both resolve the caller through the trusted-proxy client-IP resolver, so hop headers from an untrusted peer are ignored and a caller cannot select its own rate-limit bucket; a request carrying a signature-verified identity is bucketed by that identity rather than by address. No global tower `ConcurrencyLimit` or `TimeoutLayer` is wired in the builder; concurrency and timeout bounding is expected at the customer's reverse proxy / load balancer. | High-volume DoS mitigation is operational; the customer typically front-loads with a WAF / LB. |
| Expensive rule evaluation | `crates/app/runtime` | Rule evaluator has bounded complexity; no user-supplied regex/eval. | Complex allowlist configurations increase p99 linearly — benchmark before large rollouts. |
| Upstream provider slowness or oversized responses propagating back pressure | `crates/app/gateway/src/protocol/outbound/bounds.rs`, `crates/app/gateway/src/stream_tap/`, `crates/domain/ai` | Every gateway upstream call carries a first-byte deadline, an idle deadline between body chunks and a total deadline; buffered and error bodies are read through a byte cap. A stalled or oversized upstream ends as a typed error instead of holding a connection, a quota reservation and a pending audit row. A streamed response whose accumulated content passes the buffered cap ends with an error frame, and the retained audit copy of a stream is capped with truncation recorded. Agent-side providers are wrapped in a timeout/retry/circuit-breaker/bulkhead decorator (`crates/domain/ai/src/services/providers/provider_factory.rs`). Outbound MCP client requests run under a total deadline covering headers and body, read JSON responses and protected-resource metadata through a size cap, and fail a stream that stays idle past a timeout (`crates/domain/mcp/src/services/client/http_client_with_context/limits.rs`). | Governance correctness is preferred over availability — the binary fails closed. |
| Budget exhaustion by a single subject | `crates/app/gateway/src/quota/`, `crates/app/gateway/src/service/guards.rs` | Subject-keyed windows reserve one request plus an estimate of input tokens (body length), output tokens (`max_tokens`, clamped to the model ceiling) and cost at admission, and check ceilings against that total, so in-flight spend counts. Completion settles each reservation to the audited usage. A stream that ends without a usage frame settles to the larger of the reservation and the observed usage, and its audit row records `usage_source = reservation`; failure or abandonment releases the tokens and cost. A request refused under `enforce` is reversed from every window, so a denial counts in none. `quota_mode: enforce` (default) refuses with `429`; `quota_mode: warn` is a soft limit that admits the request, logs it and records the breach as a governance decision. Subject-resolution failures follow `QuotaFaultMode`. | Overshoot is bounded by one estimate per concurrent request, widened by sharding (`quota.*_subject_shards`). In `warn` mode the ceiling is not a control. |
| Audit write pressure | `crates/infra/events` | Batched writes where transactionally safe; async forwarding to SIEM so a slow SIEM cannot block the request path. | Postgres write saturation remains customer-sizeable. |

### 4.6 Elevation of Privilege

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| User escalating scope via token manipulation | `crates/infra/security`, `crates/shared/models/src/auth/permission.rs` | Scopes derive from JWT claims at entry and are immutable through the request lifecycle. Scopes grant by tier, not by a linear order: `admin` satisfies every scope, `user` satisfies `user` and `anonymous`, and each service, agent, MCP and hook scope satisfies only itself (and `anonymous`), so no service or hook token satisfies a user route; `user_type` is re-derived from the permission set and a disagreeing claim is rejected; handler-boundary RBAC re-checks at each crossing. | Relies on IdP claim correctness. |
| Extension gaining undeclared capabilities | `crates/shared/extension` | Extensions register via `inventory` at compile time; the trait surface is typed and narrow; no runtime code load. | The supply chain of compiled-in extensions is the customer's build-time decision. |
| MCP tool invoking outside declared surface | `crates/domain/mcp` | The allowlist gates every tool call; declared capabilities are enforced at call time; the server manifest pins transport and methods. | Tool servers themselves are trusted by the allowlist; customers control what they list. |
| Reaching a route that was never gated | `crates/entry/api/src/services/middleware/` | Attaching the auth context layer is only possible through `RouterExt::with_auth(auth, policy)`, which takes an `AuthzPolicy` in the same call — omitting the policy is a **compile error**, not a review miss, across all 26 call sites. `authz_gate` fails closed: a request arriving with no `RequestContext` is treated as `UserType::Anon`, so only an explicitly `public()` policy admits it. | Some routes are deliberately outside `with_auth` and authenticate in-handler: the AI gateway (bespoke credential extraction), and Slack and Teams (request-signature verification). The MCP proxy uses a deliberately deferred policy so it can emit an RFC 9728 `WWW-Authenticate` challenge. `authz_gate` is a **coarse** gate by design — per-resource ownership checks are the handler's responsibility, so a handler that forgets one is not caught by the compile-time guarantee. |
| Privilege held in shared state | All layers | No global mutable singletons; AppContext is explicit and passed through; the shared layer enforces the "no state" architectural rule. | Enforced by layer discipline and reviewed on every PR. |

### 4.7 Document store

The shared document store (`crates/domain/files/src/documents`, [documents.md](../documents.md)) adds a second class of governed object: user content shared between users, agents and devices. Its controls, by threat:

| Threat | Component | Mitigation | Residual |
|--------|-----------|------------|----------|
| A user or agent reads or edits a document it was not given | `documents/access`, `documents/service/grants.rs` | Every action checks the caller's effective level (the highest unexpired grant on the document, its folder or any ancestor, capped at `share`; `own` belongs to the owner alone and is never grantable) and then the authz hook on the nearest folder entity. A caller with no level is answered `not_found` without the owner's id, so existence is not disclosed. Listings filter in SQL with the same predicate. Document and bridge events are fan-out filtered through the recipient's effective level at emit time, so a revoked user receives no CRDT bytes. | With `files.documents.accessRequests` on, a signed-in caller's `not_found` on an existing document carries `can_request: true`, which discloses existence to signed-in users by design; the setting is off by default. |
| A share holder escalates (grants `own`, lowers a higher grant, transfers to a non-user) | `service/grants.rs`, `service/ownership.rs` | `own` is refused as `invalid_params`; a share that would lower a grant above the caller's level is refused as `forbidden` with the existing level; transfer, delete, trash, restore, move and revoke-all key on `owner_user_id == caller`, not on a level; a transfer recipient must resolve to an active user through the subject directory; an unknown user, role or dimension value is refused as `unknown_subject`. | The role catalogue and dimension listings come from the subject-attribute providers an extension registers; a provider that cannot list its values accepts any value for that dimension. |
| Sharing cannot be reconstructed after the fact | `repository/grant_events.rs` | Every grant change writes an append-only `document_grant_events` row in the same statement (event, target, subject, old and new level, expiry, actor, trace id); the presence sweep records expiries with no actor; `report_document_sharing` exposes the log. | The log is as durable as the database and its backups. |
| Office file carrying macros, OLE objects or external links | `documents/codecs/{docx,xlsx,pptx,odf}` | Codecs parse package XML with `quick-xml` and `umya-spreadsheet`, rewrite only the parts an edit touches and copy every other entry byte for byte. Nothing is executed, no external part is fetched and no subprocess is started. | A stored file is served back as uploaded; whether a client opens it with macros enabled is a client policy. |
| Preview executes script or exfiltrates | `routes/documents/history.rs` | The HTML preview is sanitised with `ammonia` and served with `Content-Security-Policy: sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:` and same-origin frame options. | Inline styles are permitted for layout fidelity. |
| Download link replay or widening | `runtime/documents/download.rs` | A download link is a user JWT with audience `documents.download`, purpose `document_download:<document>@<revision>` and a ten-minute lifetime; it opens exactly one revision of one document and nothing else. The `?format=pdf` rendition is bound the same way. | A link forwarded within its lifetime opens that revision for the bearer. |
| PDF or preview rendering reaches the network | `documents/pdf`, `documents/codecs` | PDF export is built in-process with `pdf-writer` from the rich text model or codec projection, embedding only bundled fonts; only images the revision holds are drawn and nothing is fetched; link annotations are limited to http, https and mailto; no subprocess. Page count is capped by `limits.pdfPages` (refused as `too_large`). | Text outside Latin, Greek and Cyrillic renders as U+FFFD and there is no shaping; a client needing CJK or right-to-left exports the native format. |
| Resource exhaustion through documents | `config/document_limits.rs`, `routes/documents/mod.rs` | Upload size (`maxUploadBytes`, body limit per router), operations per call, operation text, Markdown, comment, live-update and cursor sizes and PDF pages are bounded and validated at boot; a request over a limit is refused as `too_large` (413). Blob garbage collection and trash purge run in batches. | Concurrency bounding stays at the reverse proxy, as for every route. |
| Lost or duplicated writes under concurrency | `service/landing.rs`, `repository/node_ids.rs` | A commit lands revision, node ids, op-id acknowledgement and the head compare-and-swap in one transaction on the primary; a losing commit leaves no revision; node ids are reserved from a per-document counter row; an `op_id` is claimed once per user and request digest and replays its stored acknowledgement. | None identified for a single primary database. |
| Bridge Drive sync destroys or misplaces local work | `bin/bridge/src/drive/` | A remote deletion acts only on the path this device's state records for the document, never on a path the feed names. A file still holding the synced bytes moves to a local `.trash/<timestamp>/` folder (pruned after 30 days); one edited since the last sync is kept as a conflict sibling and offered for upload as a new document. A commit refused because its base is no longer the head renames the local edit to a conflict sibling and fetches the head. A gateway path that not every desktop filesystem can hold (reserved device names, trailing dots or spaces, case-folded collisions, links under the Drive folder) is not placed and stays listed as a conflict. | A conflict sibling must be reconciled by the user. |
| A device or agent acts for a user it is not | `routes/documents/drive.rs`, `runtime/documents/mcp` | Bridge Drive routes authenticate with the device bearer and act as the device's user; MCP tools authorise as the calling user, never as the server; a revision records the acting user and, for an agent, the user it acted for. | The bridge device's own custody of its bearer (see the bridge README). |

## 5. Assumptions and Non-Goals

- The customer's OS, network, and hypervisor are trusted. The binary does not defend against a malicious kernel.
- The customer's OAuth Identity Provider is trusted. Signatures are verified but IdP compromise cannot be detected.
- The customer's Postgres instance is trusted for confidentiality and integrity. Database-level encryption at rest is a customer control.
- The customer's upstream AI providers are trusted to the extent of their SLAs. The binary governs what leaves it; it does not attest what the provider does with it.
- Physical security of host infrastructure is out of scope.

## 6. Validation and review

Review affected trust boundaries when authentication, authorization, persistence, protocol
handling or integration behavior changes. Validate the configured ingress, egress, database
permissions, tenant boundaries and request retention in the deployed environment.

No third-party assessment report is included in this repository. Obtain current vendor
assessment evidence separately. Source references identify controls to inspect; they do
not establish a successful penetration test or deployment certification.
